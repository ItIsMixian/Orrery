# PO-CR-004 pilot 002: A/B/C comparison

> **Date:** 2026-08-17  
> **Status:** conditionally comparable manual apparatus pilot; insufficient for an architecture decision  
> **Authority:** research evidence only; this report does not change the released Skill or create an ADR

## Executive conclusion

Pilot 002 corrected the visible gold-fact and external-context defects found in pilot 001. All three variants received prompts and a repository overlay whose SHA-256 values match the generated manifest. At the independently observable repository boundary, every run changed only `README.md`, passed `git diff --check`, passed all three repository tests, and met both PO-CR-004 acceptance criteria. Each result is a functional, rather than exact, match to the historical reference.

The routing-cost signal is large but still directional:

- A reported seven repository content reads and took 49.761 seconds.
- B reported one repository content read and took 37.486 seconds, 24.7% less time than A.
- C reported one repository content read and took 23.558 seconds, 52.7% less time than A and 37.2% less than B.

This is evidence that the fixed seven-file entry chain imposes avoidable work on this low-risk, single-file task. It is not evidence that C is generally better than B: both selected the same one-file content set, the task did not exercise dependency discovery, and execution time came from Agent-reported timestamps without token or provider-cost measurements.

The apparatus is materially better than pilot 001, but `apparatus_valid` remains `null` rather than `true`. Prompt hashes, overlay hashes, diffs, changed paths, tests, and the historical reference were independently checked. The model, reasoning effort, and permission profile were not captured; the host did not independently log whether the overlay was loaded or which contents reached the model; and the supplied B/C final reports summarized rather than reproduced their pre-write Manifest transcripts. Those gaps prevent a strong causal policy conclusion.

## Result quality

The historical reference tells Codex in plain language to install the public GitHub path, states that the Skill becomes available on the next turn, preserves manual copying as an alternative, and then distinguishes installation from scaffolding. Its diff Git object ID is `11d5417256fafffe60308b5a670976a1d2ea980c`.

The three pilot outputs are not textually identical to that reference:

- A uses a fenced `$skill-installer install <URL>` instruction and explicitly separates installation from scaffolding, migration, and formal adoption.
- B uses the same direct fenced instruction with a shorter safety statement.
- C retains the pre-existing manual-copy option, adds the `$skill-installer` instruction as a blockquote, and preserves the adoption boundary.

All three identify the canonical repository and Skill path and avoid claiming that installation adopts the authority chain. Those are the two frozen acceptance criteria, so all three are accepted as functional matches. The historical reference remains better onboarding copy because it also explains next-turn availability and the subsequent target-repository step; that extra detail was not required by this task.

## What remains self-reported or unknown

- Original content reads, enumeration, writes, preflight status, and timestamps are Agent self-reports.
- No host or file wrapper independently recorded model-facing reads.
- There is no independent host log proving that the project overlay, although present and hash-identical, was applied by each client.
- Model family, reasoning effort, permission profile, token counts, and provider cost were not captured in the supplied records.
- No operator intervention was reported, but there is no separate operator-side transcript artifact.
- The supplied B/C final summaries do not contain the complete pre-write Context Manifest or Selected Evidence blocks, so exact declaration timing cannot be independently reconstructed.

For those reasons, the run records use `apparatus_valid: null`. This is not a failed run like pilot 001; it is a bounded manual comparison whose causal strength is not yet established.

## Interpretation by variant

### A — fixed chain

A behaved exactly as instructed and reached a correct result. Its cost is imposed by the policy: seven full reads were mandatory before a one-file edit whose normative URL and safety boundary were already in the task packet. Pilot 002 therefore provides a concrete example of fixed-chain over-reading.

### B — Context Manifest

B localized the task to `README.md`, reported one full content read, and produced a correct result with no reported expansion. It achieved the same acceptance and validation outcome as A with six fewer reported content reads.

### C — selective context

C also selected only `README.md` and produced a correct result. Its shorter wall time is interesting but cannot be attributed to selective retrieval: B reached the same one-file selection, and neither run exposed a dependency-recall challenge. C's distinguishing mechanism remains untested here.

## Next experiment gate

Do not create a routing-policy ADR from PO-CR-004 alone. Before the wider 20–30 task comparison:

1. capture model, reasoning effort, permission profile, and operator interventions in an operator-side run manifest rather than relying on the Agent;
2. preserve the complete pre-write Context Manifest and Selected Evidence transcript for B/C;
3. add host-level or controlled-wrapper access events if the platform permits, while keeping unsupported reads explicitly self-reported;
4. replay at least one medium multi-file task, one cross-module task, and one security-sensitive task from the corpus;
5. compare correctness and dependency recall before comparing speed or context volume.

Pilot 002 clears the repository-artifact portion of the apparatus. The next batch should test whether B/C preserve correctness when the necessary context is not trivially contained in one file.
