## 发布判断

- 保留版本 `0.2.0`。本计划执行前 GitHub 从未创建 Project Orrery tag 或 Release，因此不需要为了纠正未发布候选而跳到 `0.2.1` 或 `0.3.0`。
- 本轮公开发布包仍只来自 `skills/project-orrery/`。根 `docs/`、`experiments/`、自托管观测台和仓库外 benchmark 不进入 Skill zip。
- installer 排除 Python 缓存是首次 v0.2.0 发布前的缺陷修复，可以纳入同一版本。
- Context Aperture H1、Pilot 隔离实现和 compatibility-gate holdout 候选不进入发布版 Skill。

## Git 与发布顺序

1. 将当前 `codex/update-compatibility` 快进到 `origin/main`；两者文件树相同，只差远端 merge commit。
2. 按上述四个边界提交，不重写已经进入 `main` 的兼容协议历史。
3. 推送分支并等待 Windows／Ubuntu `Validate Project Orrery` 全部通过。
4. 在 CI 通过后，把 `main` 快进到该分支；无需 PR，但不得跳过分支 CI。
5. 确认 `main` CI 通过后创建并推送 `v0.2.0` tag。
6. 等待 `Release Project Orrery` 生成 zip 和 SHA-256；核对 GitHub Release、tag、下载 URL 与远端 `release-manifest.json`。
7. 以单独的 `docs(release): record v0.2.0 publication` 提交更新 State、PROGRESS、DEVLOG、HANDOFF 和日期 Snapshot，记录实际远端结果。

## 回滚

- tag 创建前：修复分支并重新跑 CI，不创建 Release。
- tag 已推送但发布工作流失败：不要移动或复用 tag；先诊断工作流，再由维护者决定删除未公开失败 tag还是发布补丁版。
